## 1. 架构要求（10 分）

### 1.1 BS 分层架构清晰，各层职责明确（3 分）

**主答成员：组员 B；补充：组员 A、组员 C。**  
**现场证据：** `templates/index.html`、`static/js/app.js`、`app.py`、`core/db.py`、`core/vision.py`。

**Q1：你们为什么说这是 BS 架构？运行在本机不就是单机程序吗？**  
**答：组员 B。** BS 架构强调浏览器和服务器职责分离，不要求服务器必须部署在远程主机。我们的浏览器页面只负责采集、上传和渲染，Flask 服务端负责 API、权限、算法和数据库操作，双方通过 HTTP 接口通信，所以是 Browser/Server 架构。

**Q2：前端、后端、数据库各自做了什么？**  
**答：组员 B。** 前端在 `templates/` 和 `static/`，负责摄像头、上传、表格和统计展示；后端 `app.py` 提供 `/api/*` 接口；数据库由 `core/db.py` 初始化 SQLite 表；算法在 `core/vision.py`，包括人脸检测、特征、活体和情绪。

**Q3：你们的算法层为什么也算一层？**  
**答：组员 C。** 因为算法没有写死在路由里，而是封装为 `detect_faces()`、`face_embedding()`、`analyze_liveness()`、`analyze_emotion()` 等函数，后续替换 InsightFace、DeepFace 时不影响 API 和前端。

**Q4：如果老师要求你画架构图，你怎么说？**  
**答：组员 B。** 浏览器端调用摄像头或上传图片，向 Flask API 发送请求；API 先做登录和权限校验，再调用视觉算法模块，最终写入 SQLite 数据库并把 JSON 结果返回前端渲染。

### 1.2 前端适配主流浏览器，界面简洁、交互友好（3 分）

**主答成员：组员 A；补充：组员 B。**  
**现场证据：** 浏览器打开 `http://127.0.0.1:5000`，展示总览、考勤、记录、学生、人脸库、合照、统计、安全自测、验收清单。

**Q1：你们前端用了什么技术？为什么不用 Vue/React？**  
**答：组员 A。** 用原生 HTML/CSS/JavaScript。课程要求允许使用 HTML/CSS/JS 或框架。我们选择原生实现是为了减少依赖、方便老师现场部署，同时已实现完整交互、响应式布局和多页面标签切换。

**Q2：摄像头调用为什么必须在 localhost 或 HTTPS 下？**  
**答：组员 A。** 浏览器安全策略要求 `getUserMedia()` 只能在安全上下文中调用，`localhost/127.0.0.1` 被浏览器视为安全来源；如果是普通 HTTP 外网地址，摄像头可能被拦截。

**Q3：如果摄像头权限被拒绝，系统会不会崩？**  
**答：组员 A。** 不会。前端 `startCamera()` 捕获异常，会提示“摄像头调用失败”，并说明检查浏览器权限、HTTPS/localhost 环境。现场还可以用无摄像头样本攻击自测兜底展示安全功能。

**Q4：界面是否区分教师和学生？**  
**答：组员 B。** 区分。前端会根据 `/api/me` 返回的角色隐藏教师功能，例如学生看不到学生管理、合照识别、安全自测等教师标签；但真正权限控制在后端，不只靠隐藏按钮。

### 1.3 后端 API 接口规范，可实现核心逻辑交互（2 分）

**主答成员：组员 B；补充：组员 A、组员 C。**  
**现场证据：** `app.py` 中 `/api/login`、`/api/attendance/check`、`/api/group/recognize`、`/api/emotions/stats` 等接口。

**Q1：你们接口规范体现在哪里？**  
**答：组员 B。** 接口统一以 `/api/` 开头；普通接口统一返回 JSON，成功包含 `ok: true` 和数据字段，失败包含 `ok: false` 和 `error`；下载接口单独返回文件流，如 Excel 和 Markdown 清单。

**Q2：前端如何处理后端错误？**  
**答：组员 A。** `static/js/app.js` 中封装了 `api()`，如果 HTTP 状态码异常或 `ok=false`，就抛出错误并显示到对应结果框，用户能看到明确原因。

**Q3：关键安全判断是在前端还是后端？**  
**答：组员 B。** 在后端。前端只是采集和展示，活体是否通过、人脸是否匹配、学生是否本人、是否有教师权限都在后端接口中判断。

**Q4：如果有人绕过前端直接请求 API 呢？**  
**答：组员 B。** 后端使用 `require_login()` 和 `require_role()` 校验 session 和角色，学生直接访问教师接口会返回 403，不能靠绕过前端获得权限。

### 1.4 数据库设计合理，数据表关联正确（2 分）

**主答成员：组员 B；补充：组员 C。**  
**现场证据：** `core/db.py` 中 `students`、`users`、`face_samples`、`attendance_records`、`emotion_records`、`activities`、`activity_participants`、`audit_logs`。

**Q1：为什么需要这么多表？能不能一个表解决？**  
**答：组员 B。** 一个表会导致数据冗余和扩展困难。我们把学生、账号、人脸样本、考勤记录、情绪记录、活动和参与关系拆开，便于查询、权限控制和统计。

**Q2：人脸特征存在什么地方？**  
**答：组员 B。** 存在 `face_samples.embedding` 字段中，以 JSON 数组形式保存特征向量，同时保存样本图片相对路径和质量分。

**Q3：情绪数据怎么和考勤、合照关联？**  
**答：组员 C。** `emotion_records` 保存 `student_id`、学号、姓名、情绪、置信度、场景 `attendance/group`、图片路径和时间。这样可以按学生或场景统计。

**Q4：活动频次怎么统计？**  
**答：组员 B。** 每次合照识别生成一条 `activities`，确认后的学生写入 `activity_participants`。统计时按学生聚合 `COUNT(*)`，得到参与频次。

## 2. 基础考勤功能（25 分）

### 2.1 摄像头调用正常、人脸采集流畅（3 分）

**主答成员：组员 A；补充：组员 C。**  
**现场证据：** “考勤打卡”页面点击“开启摄像头”。

**Q1：摄像头采集是实时的吗？**  
**答：组员 A。** 是。浏览器通过 `navigator.mediaDevices.getUserMedia()` 获取实时视频流，显示在 `<video>` 标签中。采集时再把当前画面绘制到 canvas 并转成 base64 图片帧。

**Q2：为什么不把视频流一直传给后端？**  
**答：组员 A。** 为了减少传输和处理压力。前端只在手动预检或活体阶段采集关键帧，后端处理多帧图片即可完成活体和识别。

**Q3：如果视频画面卡顿，会影响考勤吗？**  
**答：组员 A。** 会影响帧质量，所以系统会根据有效人脸帧数、质量分和动作变化判断；帧数不足或画质太差会返回失败提示，而不是误判成功。

**Q4：后端如何从摄像头帧中找到人脸？**  
**答：组员 C。** 后端把 base64 解码成 OpenCV 图像，然后用 Haar 正脸/侧脸检测，选取质量最高的人脸框进行裁剪和特征提取。

---

### 2.2 支持手动/自动捕捉并显示采集状态（3 分）

**主答成员：组员 A；补充：组员 C。**  
**现场证据：** “手动抓拍预检”“开始活体打卡”“采集状态”步骤列表。

**Q1：手动抓拍和自动捕捉有什么区别？**  
**答：组员 A。** 手动抓拍只采集一帧，用于质量、人脸候选和情绪预检，不写入考勤。自动捕捉是在随机动作挑战中分阶段采集多帧，用于正式打卡。

**Q2：手动抓拍会不会成为漏洞？**  
**答：组员 A。** 不会。手动接口 `/api/attendance/preview` 明确不写入 `attendance_records`。正式考勤必须走 `/api/attendance/challenge` 和 `/api/attendance/check`。

**Q3：采集状态如何显示？**  
**答：组员 A。** 前端把后端返回的动作步骤渲染成列表，当前阶段高亮，完成后标记 done，同时结果框实时提示正在采集第几段。

**Q4：自动捕捉的帧数是多少？为什么？**  
**答：组员 A。** 正式打卡现在分为 3 组随机动作，每组最多 5 秒。前端会连续采帧并调用单组检测接口，只有检测到当前动作通过后才进入下一组；最终仍由后端对全部帧重新做总体验证。

**答：组员 A。** 返回考勤状态、姓名、学号、时间、活体通过情况、活体分、人脸匹配分、情绪类型和置信度、备注。

**Q3：考勤结果是否真的入库？**

**答：组员 B。** 失败记录可以用于审计和安全分析，例如发现重复的照片攻击或异常打卡行为。

**主答成员：组员 A；补充：组员 B。**  
**现场证据：** “考勤记录”页面输入学号、开始日期、结束日期。

### 2.5 活体检测功能正常，可抵御照片、视频欺骗（10 分）

**主答成员：组员 A；补充：组员 C。**  
**现场证据：** “开始活体打卡”“安全自测”“无摄像头样本攻击自测”“展示随机挑战抗视频”。

**Q1：活体检测的核心逻辑是什么？**  
**答：组员 A。** 后端随机生成动作挑战，前端按阶段采集多帧。后端检查人脸中心位置、面积变化、有效帧数、画面质量、重复帧比例和平均帧差，综合判断是否通过。

**Q2：如何抵御照片攻击？**  
**答：组员 C。** 静态照片或重复帧会导致感知哈希重复率高、平均帧差低、动作变化不足。安全自测会复制同一张图构造攻击帧，后端返回“检测到重复静态帧，疑似照片/重放攻击”。

**Q3：如果拿着照片左右移动呢？**  
**答：组员 A。** 移动照片可能产生部分位置变化，但系统还检查多阶段动作、面积变化、帧差和质量。课程系统能抵御典型静态照片和简单重放；更高强度攻击可加入眨眼、张嘴、随机读数字等增强措施。

**Q4：如何抵御视频重放？**  
**答：组员 C。** 挑战由后端实时随机生成，动作池包含 9 种动态动作，每次随机抽取 3 组有序动作，共 9×8×7=504 种组合；每组最多 5 秒，必须检测到当前动作后才进入下一组，并且整次挑战 90 秒过期。预录视频不知道本次动作顺序、限时节奏和逐组判定结果，难以提前匹配。

**Q5：如果攻击者录制所有动作组合呢？**  
**答：组员 C。** 现在已经从原来的少量动作增强为 9 种动作池、3 组限时挑战，组合空间达到 504 种；如果要生产级防护，还可以继续叠加随机读数字、眨眼/张嘴、屏幕闪烁反光检测和深度活体模型。

**Q6：为什么不用深度学习活体模型？**  
**答：组员 C。** 课程现场要保证离线部署和可运行性，所以采用轻量动作活体。我们已把活体逻辑封装，后续可以替换或叠加深度模型。

**Q7：活体检测阈值在哪里体现？**  
**答：组员 C。** `analyze_liveness()` 综合动作、质量、有效帧比例、重复帧指标计算 score，要求分数、动作、质量和时间一致性同时满足。

**Q8：为什么活体判断不能放在前端？**  
**答：组员 A。** 前端代码可被用户修改，安全判断必须在后端完成。我们的后端会重新解码每一帧并计算活体结果。

### 2.6 班级人脸库可批量导入、单个添加/删除/修改（2 分）

**主答成员：组员 B；补充：组员 C。**  
**现场证据：** “学生/人脸库”页面；`scripts/import_face_data.py`；样本查看/删除面板。

**Q1：如何批量导入老师给的 face_data？**  
**答：组员 B。** 运行 `python scripts\prepare_demo.py` 或 `python scripts\import_face_data.py --source ..\face_data`。脚本解析文件名中的学号、姓名、专业、性别，自动创建学生并提取人脸样本。

**Q2：如果某张照片导入失败怎么办？**  
**答：组员 B。** 失败不会静默忽略，会写入 `docs/face_data_import_report.json`。当前失败 1 张，原因是未检测到清晰人脸，教师可以用更清晰图片或摄像头补采。

**Q3：单个添加体现在哪里？**  
**答：组员 B。** 教师可以在学生管理表单新增学生，也可以对某学生上传单张或多张人脸图片，还可以用摄像头补采样本。

**Q4：单个删除和修改体现在哪里？**  
**答：组员 B。** 学生信息支持编辑和删除；新版本还增加了样本级查看/删除，可以删除某个学生的单个人脸样本，不必删除整个学生。

**Q5：人脸库中的样本质量如何维护？**  
**答：组员 C。** 每个样本有质量分，教师可以查看样本图和质量分，删除模糊、遮挡或误导入样本，提升识别准确率。

**Q6：一个同学上传多张图片时，系统怎么利用这些图片？**  
**答：组员 C。** 现在不是逐张样本互相独立抢最高分，而是按学生聚合：先算该学生所有样本与待识别人脸的相似度，再综合最高分、TopK 均值和稳定样本数得到学生级分数。因此同一个学生上传多张不同光照、角度、表情的高质量图片，识别会更稳；低质量样本可在样本面板删除，避免干扰。

## 3. 合照学生识别功能（9 分）

### 3.1 支持前端上传合照，后端检测并批量识别人脸（3 分）

**主答成员：组员 C；补充：组员 B。**  
**现场证据：** “合照识别”页面上传 `storage/uploads/demo_collage_*.png`。

**Q1：合照识别的完整流程是什么？**  
**答：组员 C。** 前端上传图片，后端解码图片，检测多个人脸框，对每张脸裁剪、提取特征、与人脸库比对，同时分析情绪，最后返回标注图和识别表格。

**Q2：如果一张合照中有多个相似的人怎么办？**  
**答：组员 C。** 系统按学生聚合多样本分数，不仅看最高相似度，还返回第二名分数和分差。合照识别默认要求第一名超过阈值，并与第二名有一定间隔，降低误识别。

**Q3：如果合照里有不在班级的人怎么办？**  
**答：组员 C。** 低于阈值或分差不足会显示未匹配或待确认，不会自动写入参与名单。教师确认时只能选择系统学生库中的学生。

**Q4：合照标注图如何生成？**  
**答：组员 C。** 后端 `annotate_group_image()` 在图片上画人脸框、姓名/unknown、匹配分和情绪，然后保存到 `storage/annotated`，前端显示标注图。

**Q5：如果老师现场换一张模糊合照，准确率下降怎么办？**

## 4. 情绪分析功能（8 分）

### 4.1 考勤、合照识别过程中同步提取面部特征并完成情绪分类（5 分）

**Q1：情绪分析在哪里触发？**

**Q2：情绪分类有哪些类别？**  
**答：组员 C。** 当前支持 `neutral`、`happy`、`surprise`、`sad`、`angry`，并返回置信度和各类别得分。

**Q3：情绪算法依据是什么？**  
**答：组员 C。** 当前是轻量启发式方法，分析眼部、口部区域暗区比例、边缘强度、亮度、对称性等特征，适合课程离线演示。

**答：组员 C。** 不是生产级心理判断。我们明确把它作为课程端到端链路实现，后续可以替换 FER、DeepFace 等模型，而不影响接口和前端。

**Q5：为什么情绪分析也属于内容安全？**  
**答：组员 C。** 内容安全不仅关注身份真实性，还关注图像内容理解。情绪分析体现对人脸内容的进一步理解和统计，但也需要注意隐私和使用边界。

## 5. 系统安全（18 分）

### 5.1 活体检测抗照片伪造攻击（7 分）

**主答成员：组员 A；补充：组员 C。**  
**现场证据：** “安全自测”中的“运行静态照片攻击自测”“无摄像头样本攻击自测”。

**Q1：照片攻击自测如何构造？**  
**答：组员 C。** 系统截取一帧或使用库内样本，把同一张图复制成多个阶段的帧，模拟静态照片/重复帧攻击，再交给真实活体检测函数判断。

**Q2：期望结果是什么？**  
**答：组员 A。** 期望失败。页面会显示实际活体“拒绝”，原因通常是“检测到重复静态帧，疑似照片/重放攻击”。

**Q3：如果照片稍微晃动，会不会通过？**  
**答：组员 C。** 系统还看随机动作阶段是否符合、面积变化是否合理、质量和帧差是否满足。简单晃动不等于按挑战完成动作。

**Q4：照片攻击为什么不只靠人脸识别分数判断？**  
**答：组员 A。** 因为照片上的脸可能和本人高度相似，仅靠人脸识别会被欺骗，所以必须先判断活体，再判断身份。

---

### 5.2 活体检测抗视频伪造攻击（8 分）

**主答成员：组员 C；补充：组员 A。**  
**现场证据：** “展示随机挑战抗视频”；正式考勤挑战步骤。

**Q1：视频攻击和照片攻击有什么区别？**  
**答：组员 C。** 视频有运动，不一定是重复帧，所以除了重复帧检测，还需要随机挑战响应，让攻击者无法提前知道本次动作顺序。

**Q2：你们如何证明随机性？**  
**答：组员 C。** “展示随机挑战抗视频”接口展示 9 种动作池、3 组随机挑战、504 种有序组合、单组 5 秒限时和 90 秒过期。正式考勤每次从动作池随机抽取 3 组，并且前端检测到当前组动作通过后才进入下一组。

**Q3：如果攻击者提前录好多种视频呢？**  
**答：组员 C。** 课程版提高了攻击成本。生产环境可以增加随机读数字、眨眼、张嘴、头部方向、屏幕闪烁反光检测，让预录覆盖成本指数级增加。

**Q4：挑战过期有什么意义？**  
**答：组员 A。** 防止攻击者拿旧 challenge 重放。后端检查 challenge_id 和创建时间，超过 90 秒会要求重新开始。

**Q5：挑战是否可以被前端伪造？**  
**答：组员 A。** 不可以。挑战保存在后端 session，提交时必须匹配当前 session 中的 challenge_id 和动作列表。

### 5.3 教师、学生账号权限区分与异常防护（3 分）

**主答成员：组员 B；补充：组员 A、组员 C。**  
**现场证据：** 教师账号 `teacher/teacher123`，学生账号 `student01/student123`；直接访问教师接口返回 403。

**Q1：教师和学生权限具体区别是什么？**  
**答：组员 B。** 教师可以管理学生、人脸库、合照、安全自测、查看全部记录；学生只能查看本人考勤、本人活动频次和本人情绪统计。

**Q2：权限是在前端还是后端实现？**  
**答：组员 B。** 两边都有。前端根据角色隐藏功能；后端用装饰器和 SQL 条件强制校验，后端才是安全边界。

**Q3：学生能不能通过改 URL 下载别人照片？**  
**答：组员 B。** 新版本已补强 `/storage` 权限，学生只能访问自己 `face_samples` 中登记的图片路径，不能随意猜路径访问其他文件。

**Q4：上传异常图片会怎么样？**  
**答：组员 C。** 图片解码失败会返回错误；样本上传检查扩展名；Flask 配置了上传大小上限，避免超大文件拖垮服务。

**Q5：系统有哪些异常提示？**  
**答：组员 A。** 摄像头失败、挑战过期、采集帧数不足、无人脸、图片解析失败、权限不足、上传失败等都会给出明确提示。
