## 3. 三人平均分工方案

### 3.1 分工原则

不要把三个人简单分成“前端、后端、算法”，因为那样工作量不均，也不利于答辩。当前系统更适合按完整业务闭环分工：每个人都承担前端、后端、安全、测试和报告的一部分。

| 成员 | 主负责闭环 | 工作量占比 | 核心展示能力 |
|---|---|---:|---|
| 组员 A | 基础考勤与活体打卡闭环 | 33% | 摄像头、手动/自动采集、活体考勤、记录查询 |
| 组员 B | 数据库、权限、人脸库与导出闭环 | 33% | 登录权限、学生管理、人脸库、Excel、审计 |
| 组员 C | 合照识别、情绪分析与算法评测闭环 | 34% | 合照批量识别、统计报表、情绪、安全评测 |

### 3.2 组员 A：基础考勤与活体打卡闭环，约 33%

**负责内容：**

- 前端：摄像头开启、实时视频预览、手动抓拍预检、自动活体采帧、考勤状态显示。
- 后端：参与 `/api/attendance/challenge`、`/api/attendance/preview`、`/api/attendance/check`、`/api/attendance`。
- 安全：活体交互流程、随机动作挑战、挑战过期、摄像头失败/识别超时/无人脸异常处理。
- 测试：真人考勤、静态照片失败、挑战过期、考勤记录筛选。
- 报告：基础考勤功能实现、考勤流程图、考勤测试用例。

**现场展示：**

1. 开启摄像头。
2. 手动抓拍预检，说明“不写入考勤”。
3. 开始活体打卡，按随机动作完成采集。
4. 展示姓名、学号、状态、时间、活体分、人脸分、情绪。
5. 到考勤记录页按日期/学号筛选。

**答辩重点说法：**

- 手动抓拍只做预检，不允许直接打卡，避免单帧照片绕过活体。
- 正式考勤必须通过后端 session 中的随机挑战。
- 多帧提交到后端后统一判断，前端不能自己决定是否通过。

### 3.3 组员 B：数据库、权限、人脸库与导出闭环，约 33%

**负责内容：**

- 前端：登录页、教师/学生页面差异、学生管理、人脸样本查看/删除、Excel 导出入口。
- 后端：`students`、`users`、`face_samples`、`attendance_records`、`emotion_records`、`activities`、`activity_participants`、`audit_logs` 表设计。
- 安全：教师/学生接口权限、学生只能查看本人数据、上传图片格式和大小限制、存储路径防穿越。
- 测试：教师登录、学生登录、越权访问、学生 CRUD、样本上传/删除、Excel 导出。
- 报告：数据库设计、接口设计、权限控制、部署说明。

**现场展示：**

1. 教师登录后查看所有功能标签。
2. 学生登录后只能看到个人相关功能。
3. 教师新增/编辑/删除学生。
4. 上传人脸样本、查看样本、删除单个样本。
5. 导出 Excel。
6. 展示审计日志和验收清单。

**答辩重点说法：**

- 权限不仅在前端隐藏按钮，后端接口也使用 `require_role()` 校验。
- 学生查询考勤、活动、情绪时都会自动追加 `student_id` 条件。
- `/storage` 文件访问也限制学生只能访问自己的样本，防止直接猜路径。

### 3.4 组员 C：合照识别、情绪分析与算法评测闭环，约 34%

**负责内容：**

- 前端：合照上传、标注图展示、逐脸结果表、教师确认/补选名单、统计柱状图、安全自测页面。
- 后端：`/api/group/recognize`、`/api/group/<id>/participants`、`/api/group/stats`、`/api/emotions/stats`、`/api/liveness/self-test-sample`。
- 算法：人脸检测、LBP/HOG/DCT 特征、人脸比对阈值、情绪分类、合照标注。
- 安全：照片/视频伪造攻击解释、随机挑战说明、阈值误识别风险分析。
- 测试：10 人合照自测、50 人压力合照自测、情绪统计、最终验收脚本。
- 报告：算法设计、准确率分析、结果分析、改进方案。

**现场展示：**

1. 上传 10 人演示合照。
2. 展示检测框、学号姓名名单、情绪结果。
3. 确认最终参与名单。
4. 展示活动频次柱状图。
5. 展示 50 人压力测试报告。
6. 运行安全自测，展示重复帧攻击被拒绝。

**答辩重点说法：**

- 自动识别使用阈值和第一/第二候选分差降低误识别。
- 合照场景加入教师确认，是为了真实系统安全：宁可人工确认低置信样本，也不盲目写入。
- 情绪分析当前是轻量启发式模型，课程目标是完成端到端链路，后续可替换 DeepFace/FER。

## 5. 老师可能追问与标准回答

### 5.1 架构与工程实现

**Q1：为什么说你们是 BS 架构？不是单机程序吗？**  
A：浏览器只负责交互、摄像头采集和页面渲染；Flask 后端提供 `/api/*` 接口处理业务和算法；SQLite 负责持久化存储。即使部署在本机，也是 Browser/Server 分层，浏览器和服务器通过 HTTP API 通信。

**Q2：前后端职责怎么划分？**  
A：前端负责调用摄像头、上传图片、展示结果；后端负责活体检测、人脸识别、情绪分析、权限校验、数据库写入。关键安全判断全部在后端，前端不能决定考勤是否成功。

**Q3：为什么不用 Vue/React？**  
A：课程要求允许 HTML/CSS/JavaScript 或框架。我们使用原生前端减少依赖，便于现场部署，同时已实现响应式布局、表格、统计图和完整交互。

**Q4：数据库为什么选 SQLite，不用 MySQL？**  
A：要求允许任选数据库。SQLite 适合课程设计现场展示，部署简单、无需额外服务；表结构和 SQL 设计可平滑迁移到 MySQL。

**Q5：系统如何保证接口规范？**  
A：接口统一以 `/api/` 开头，JSON 返回包含 `ok`、结果字段或 `error`；下载类接口单独返回文件流，例如 Excel 和 Markdown 清单。

### 5.2 基础考勤

**Q6：手动抓拍是否可以绕过活体检测？**  
A：不能。手动抓拍接口 `/api/attendance/preview` 只做预检，不写入考勤记录；正式打卡必须调用 `/api/attendance/challenge` 获取随机挑战，再通过 `/api/attendance/check` 的多帧活体检测。

**Q7：自动捕捉体现在哪里？**  
A：点击“开始活体打卡”后，前端按后端返回的动作步骤自动分阶段采集多帧，每阶段约采集 6 帧，最后统一提交后端。

**Q8：考勤成功的判定条件是什么？**  
A：同时满足活体检测通过、人脸库匹配成功、如果是学生账号还必须匹配本人。任一条件不满足都记录为失败或返回错误。

**Q9：如果一个学生帮另一个学生登录打卡呢？**  
A：学生账号打卡时，后端会检查识别出的 `student_id` 是否等于当前登录账号绑定的 `student_id`。不一致则失败并写入备注“学生账号只能为本人打卡”。

**Q10：摄像头打不开怎么办？**  
A：前端会提示浏览器权限、HTTPS/localhost 环境问题。现场兜底可以用“无摄像头样本攻击自测”证明安全点，记录查询和合照识别也可以继续展示。

**Q11：考勤记录如何查询？**  
A：`/api/attendance` 支持 `student_no`、`start`、`end` 参数；教师可查全部，学生自动限制为本人记录。

**Q12：Excel 导出是否区分权限？**  
A：区分。教师导出全部考勤，学生只导出本人考勤，这是在后端 SQL 层做的，不是前端控制。

### 5.3 活体检测与抗攻击

**Q13：你们如何抵御照片攻击？**  
A：照片攻击通常是静态画面。系统检测多帧的感知哈希重复率、平均帧差、人脸中心/面积变化。如果重复帧比例过高或动作不符合挑战，会返回“检测到重复静态帧，疑似照片/重放攻击”。

**Q14：如果拿照片在摄像头前左右移动呢？**  
A：移动照片可能产生位置变化，但纹理质量、阶段动作和自然运动仍会被综合判断。更严格的生产方案可加眨眼、张嘴、屏幕反光检测；本课程系统已实现随机动作和重复帧检测，并提供改进方向。

**Q15：如何抵御预录视频？**  
A：正式考勤前由后端随机生成两步动作挑战，挑战写入 session，90 秒过期。预录视频不知道本次动作组合和顺序，难以提前覆盖。后端还检查每个阶段的人脸中心和面积变化是否符合动作。

**Q16：随机动作只有四种，会不会太少？**  
A：当前是课程演示版，四种动作两两排列有 12 种组合，已能体现挑战-响应机制。后续可扩展眨眼、张嘴、读随机数字等动作，提高组合空间。

**Q17：活体检测是在前端还是后端？**  
A：后端。前端只采集帧和展示提示，`analyze_liveness()` 在后端执行，因此用户不能通过改前端 JS 直接让考勤成功。

**Q18：如果有人重放前端请求呢？**  
A：请求必须带当前 session 中的 challenge_id，而且挑战 90 秒过期；成功或失败处理后会清除挑战。重放旧 challenge 会失败。

### 5.4 人脸库与识别

**Q19：人脸库怎么建立？**  
A：老师提供的 `face_data` 文件名包含学号、姓名、专业、性别。导入脚本解析文件名，检测人脸，裁剪人脸，提取特征，写入 `students` 和 `face_samples`。

**Q20：为什么有 1 张导入失败？**  
A：失败样本数量以本地 `docs/face_data_import_report.json` 为准，典型原因是未检测到清晰人脸。系统保留失败报告，说明不是静默丢弃，后续可让教师用摄像头或更清晰照片补采。

**Q21：人脸样本能不能单独删除？**  
A：可以。已补充“样本”按钮，教师可查看某学生所有样本，并删除低质量或误导入的人脸样本，学生信息不会被删除。

**Q22：为什么每人只有一张样本也能识别？**  
A：当前使用 LBP、HOG、DCT 等轻量特征，能在正脸、光照较好时工作。报告中也说明每人 3–5 张不同光照/角度样本会进一步提升鲁棒性。

**Q23：阈值为什么设置为 0.78？**  
A：0.78 在当前样本库上兼顾召回和误识别风险。评估报告显示阈值越高误接收率越低；如果老师更强调安全，可临时调到 0.85 或 0.90。

**Q24：人脸识别准确率如何证明？**  
A：用真实接口自测：10 人演示合照检测 10 人、匹配 10 人，recall=1.0、precision=1.0；50 人压力合照也生成对应报告，证明可处理评分范围上限。

### 5.5 合照识别

**Q25：合照识别流程是什么？**  
A：教师上传图片，后端检测所有人脸，对每个人脸提取特征并与人脸库比对，返回标注图、每张脸的候选学生、匹配分、情绪；自动匹配写入活动参与表。

**Q26：为什么还要教师确认？自动识别不就够了吗？**  
A：真实考勤系统要避免低置信误识别，所以采用“自动识别 + 教师确认/补选”闭环。高置信自动加入，低置信候选由教师确认，缺漏人员可补选。

**Q27：如果合照中有陌生人怎么办？**  
A：低于阈值或分差不足会显示 unknown/待确认，不会自动写入学生参与名单。教师确认时也只能从学生库选择。

**Q28：如何满足 10–50 人要求？**  
A：现场主展示 10 人合照，稳定达到 100%；另有 50 人压力合照和 `group_collage_50_selftest_report.json`，用于证明系统处理上限规模。

**Q29：50 人压力图是不是拼图，不是真实活动照片？**  
A：它是压力测试图，用老师授权的真实学生人脸样本拼接生成，目的是稳定验证 10–50 人处理能力。真实活动照片也可上传，只是受清晰度、遮挡、角度影响更大，所以系统提供教师确认机制。

**Q30：合照识别为什么能生成活动频次？**  
A：每次活动写入 `activities`，识别/确认后的学生写入 `activity_participants`。统计接口按学生聚合 `COUNT(*)`，前端展示柱状图。

### 5.6 情绪分析

**Q31：情绪分析用了什么模型？**  
A：当前为离线启发式模型，根据眼部、口部、边缘、亮度、对称性等特征，将表情分为 neutral、happy、surprise、sad、angry，并给出 confidence。

**Q32：为什么不用深度学习情绪模型？**  
A：课程现场部署要保证离线可运行、依赖少。我们把情绪分析封装在 `analyze_emotion()`，后续可无缝替换 DeepFace/FER，不影响接口和前端。

**Q33：情绪分析准确吗？**  
A：它能完成课程要求的同步分类和统计链路，但不是生产级心理判断。报告中明确说明局限和改进方向。现场重点展示记录完整性：学号、姓名、时间、场景、情绪类型。

**Q34：情绪数据如何关联学生？**  
A：考勤和合照识别出学生后，写入 `emotion_records`，包括 `student_id`、`student_no`、`name`、`emotion`、`confidence`、`scene`、`captured_at`。

### 5.7 权限与隐私

**Q35：教师和学生权限如何区分？**  
A：用户表 `users` 有 `role` 字段。后端使用 `require_login()` 和 `require_role('teacher')` 装饰器控制接口；学生查询接口自动加本人 `student_id` 条件。

**Q36：前端隐藏按钮是否足够？**  
A：不只靠前端。前端隐藏只是用户体验，真正权限校验在后端。学生直接请求教师接口会返回 403。

**Q37：学生能不能访问别人的照片路径？**  
A：已补强 `/storage` 权限：学生只能访问自己 `face_samples` 中的图片路径，不能随便猜测其他文件路径。

**Q38：人脸隐私如何处理？**  
A：只使用老师授权的班级照片，数据保存在本地 `storage/` 和 `data/app.db`，不上传外部服务；提交源码时可不打包人脸数据，使用 `scripts/prepare_demo.py` 在本地重新生成。

**Q39：是否有审计日志？**  
A：有。登录、登出、学生管理、人脸上传/删除、考勤、合照识别、确认名单、安全自测等关键操作都会写入 `audit_logs`。

### 5.8 异常处理与部署

**Q40：上传非图片会怎样？**  
A：后端使用 OpenCV 解码，失败会返回“无法解析图片”；样本上传还检查扩展名；Flask 设置 `MAX_CONTENT_LENGTH` 限制上传大小。

**Q41：识别超时或未检测到人脸怎么办？**  
A：接口返回明确错误，例如“未检测到清晰人脸”“采集帧数不足”“活体挑战已过期”，前端用结果框展示，不会崩溃。

### 5.9 报告与分工

**Q44：报告是否覆盖评分标准全部内容？**  
A：覆盖。报告包含需求分析、系统设计、数据库设计、接口设计、算法设计、核心代码、测试用例、结果分析、问题与改进、总结展望。

**Q45：三个人是否平均分工？**  
A：是。我们不是按前端/后端/算法机械切分，而是按三个完整业务闭环切分。每个人都有前端、后端、安全、测试、报告任务，工作量约 33%、33%、34%。

**Q46：每个人答辩时能展示什么？**  
A：组员 A 展示基础考勤和活体；组员 B 展示数据库、权限、人脸库、导出；组员 C 展示合照识别、情绪分析、安全评测和准确率报告。

**Q47：如果老师现场要求随机挑一个得分点展示怎么办？**  
A：打开“验收清单”页面。该页面把每个评分点映射到功能页面、接口和证据，可按任意得分点快速跳转讲解。
