# 新版本三人平均分工说明

> 项目：基于 BS 架构的班级智能考勤系统  
> 分工原则：不按“前端/后端/算法”机械拆分，而按完整业务闭环拆分。每名成员都承担前端、后端、安全、测试和报告任务，保证工作量接近，并且每个人都能在答辩现场独立展示自己负责的模块。

---

## 1. 新版本系统模块工作量评估

| 模块 | 主要内容 | 工作量占比 | 难点说明 |
|---|---|---:|---|
| BS 架构与接口 | Flask API、前后端交互、项目结构、统一错误处理 | 8% | 需要保证全系统接口稳定 |

| 基础考勤后端 | 挑战生成、正式打卡、记录入库、查询筛选 | 10% | 需要和活体、人脸库、权限联动 |
| 活体检测安全 | 随机动作、多帧运动、重复帧检测、抗照片/视频 | 14% | 安全得分高，现场必须能证明 |
| 数据库与权限 | 用户、学生、样本、考勤、活动、情绪、审计表 | 12% | 表结构多，权限必须后端强校验 |

| 测试与验收脚本 | smoke、10 人合照、50 人压力、final acceptance | 8% | 支撑现场“每个得分点可展示” |
| 报告与答辩材料 | 课程报告、验收清单、刁钻问答、部署说明 | 7% | 需要覆盖评分标准每一项 |
| **合计** |  | **100%** |  |

根据工作量，新版本仍采用三个闭环平均分配：

## 2. 组员 A 分工：基础考勤与活体打卡闭环，约 33%

### 2.1 主负责目标

组员 A 负责“学生从浏览器摄像头进入系统，到完成一次正式活体考勤，再到前端展示和记录查询”的完整闭环。

### 2.2 前端任务

| 任务 | 对应文件/页面 | 说明 |
|---|---|---|
| 摄像头调用 | `static/js/app.js`、考勤打卡页 | 使用 `getUserMedia()` 打开摄像头并显示实时视频 |
| 手动抓拍预检 | 考勤打卡页“手动抓拍预检” | 单帧采集，显示人脸质量、候选匹配、情绪，不写入考勤 |
| 自动活体采帧 | 考勤打卡页“开始活体打卡” | 按后端随机挑战分阶段自动采集多帧 |
| 采集状态显示 | `challengeSteps`、`attendanceMsg` | 显示当前动作、阶段进度、成功/失败原因 |
| 考勤结果渲染 | 考勤结果框 | 展示姓名、学号、状态、时间、活体分、人脸分、情绪 |
| 考勤记录查询交互 | 考勤记录页 | 支持学号、开始日期、结束日期筛选 |

### 2.3 后端任务

| 任务 | 对应接口/函数 | 说明 |
|---|---|---|
| 活体挑战生成 | `/api/attendance/challenge` | 生成随机动作挑战并写入 session |
| 手动预检 | `/api/attendance/preview` | 质量、人脸候选、情绪预检，不写考勤 |
| 正式考勤提交 | `/api/attendance/check` | 接收多帧，调用活体、人脸识别、情绪分析并写入记录 |
| 考勤记录查询 | `/api/attendance` | 按学号、日期筛选；学生只能查本人 |
| 考勤异常处理 | 相关接口 | 摄像头帧为空、挑战过期、帧数不足、无人脸等提示 |

### 2.4 安全任务

- 设计随机动作挑战流程，避免单张照片直接打卡。
- 保证手动抓拍只做预检，不写入考勤记录。
- 配合组员 C 验证静态照片/重复帧攻击会被拒绝。
- 解释挑战过期、session challenge、防请求重放逻辑。
- 处理摄像头失败、识别超时、无人脸等异常。

### 2.5 测试任务

|---|---|---|

| A-T03 | 正常真人活体打卡 | 活体通过，匹配成功则考勤成功 |

## 6. 每个人答辩时的核心话术

### 6.1 组员 A 核心话术

我主要负责基础考勤和活体打卡闭环。前端通过浏览器调用摄像头，支持手动抓拍预检和正式随机动作打卡。手动抓拍只做质量、候选和情绪预检，不写入考勤，避免绕过活体。正式考勤由后端从 10 种单动作池随机生成 3 组挑战，每组最多 5 秒；前端检测到当前动作通过后才进入下一组，最终后端根据人脸位置、面积变化、质量、重复帧和帧差综合判断活体，再做人脸匹配和情绪分析，最后写入考勤记录。

### 6.2 组员 B 核心话术

我主要负责数据库、权限、人脸库和部署导出闭环。系统使用 SQLite 设计了学生、用户、人脸样本、考勤、情绪、活动参与、审计等表。权限上区分教师和学生，教师能管理全部数据，学生只能查看本人相关记录。新版本还补充了人脸样本级查看和删除，方便剔除低质量样本。Excel 导出和 storage 文件访问也都在后端做了权限控制。

### 6.3 组员 C 核心话术

我主要负责合照识别、情绪分析、算法评测和安全自测。系统用 OpenCV 检测人脸，用 LBP/HOG/DCT 等轻量特征做人脸比对，并通过学生级多样本聚合、阈值和第一/第二候选分差降低误识别。合照识别支持自动识别和教师确认，能够生成活动参与名单和频次统计。情绪分析在考勤和合照中同步执行。安全方面，我们提供静态照片/重复帧攻击自测和随机挑战抗视频说明，并用 10 人和 50 人合照自测报告证明识别能力。

## 7. 工作量均衡性说明

这套分工的平均性体现在：

1. **每个人都有前端任务。**  
   A 做考勤和摄像头；B 做登录、学生管理和样本面板；C 做合照、统计和安全自测。

2. **每个人都有后端任务。**  
   A 做考勤接口；B 做数据库、权限和导出接口；C 做合照、情绪和安全自测接口。

3. **每个人都有安全任务。**  
   A 做活体流程和挑战过期；B 做权限、路径和上传防护；C 做攻击自测、阈值和算法风险分析。

4. **每个人都有测试和报告任务。**  
   A 写考勤测试和基础考勤报告；B 写权限、数据库、部署和源码说明；C 写算法、准确率、安全自测和结果分析。

5. **每个人都能独立现场展示。**  
   A 展示考勤闭环；B 展示数据权限闭环；C 展示合照情绪算法闭环。

因此，新版本分工不是简单拆页面或拆代码文件，而是按照三个可验收的业务闭环分配，工作量基本相等，也方便答辩时每个人都有足够贡献可讲。
